## Step 2 — Run a lean recency-first search pass

## Step 3 — Filter and score



For each result, ask: does this describe a **real, specific deployment** of OpenClaw / Hermes / a Claude agent **running autonomously** in an actual workflow? The agent must be the *actor* — doing things on its own, not merely assisting a human who is doing the work. Also ask: is it recent enough to deserve one of today’s slots?

**The core litmus test:** After the thing described is done, is an OpenClaw / Hermes / Cowork / Claude agent *still* running and doing things autonomously? If the answer is no — if the "agent" was just a one-off assistant the human directed — discard the result.

Discard:

- Generic tutorials, how-to guides, Anthropic marketing

- Speculation or "I’m thinking of building..." posts

- Results matching any URL/ID from Step 1 (dupes)

- Near-duplicates of each other (same use case, different post)

- Older candidates that are weaker than available newer candidates

- **"Built with Claude/AI" stories** — posts where a person used Claude Code, Claude chat, or any LLM *as a coding or writing assistant* to build a product, but the finished product itself does not contain or run an agent. Example to reject: "I used Claude Code to help me write the Rust core of my macOS app." The finished app is not an agent — discard. This also covers automated build pipelines: a shell script that loops Claude invocations overnight to produce 50 static browser tools is still a build process, not an agentic deployment — however impressive the tooling or however parallel/automated the build was. The question is never how the building happened; it's whether an agent is operating autonomously in the finished result. The test: does the *deployed product or workflow* contain an agent that keeps running after the build phase?

- **One-shot prompting showcases** — a single human prompt produces a single output, even if the output is impressive. Must involve scheduling, memory, sub-agents, iteration, or a multi-step autonomous pipeline to qualify.

- **Pure product-announcement posts** with no workflow evidence — a launch tweet or ProductHunt card that describes what a product *will* do, with no sign of real users or a running deployment.

- **Comparison / overview articles** that survey the agent landscape but do not themselves document any specific deployment (e.g. "OpenClaw vs Claude Cowork" roundups, "Top 10 use cases" listicles).

**Three-part test for a core record** (no `increaseScope`): a qualifying use case must have ALL THREE of: (1) a named operator or author, (2) a named specific workflow, and (3) a documented outcome or result. If it only passes 1 or 2 of these, do not discard it — instead include it but tag it with `increaseScope` using the appropriate label below.

**Include with `increaseScope`** for entries that have real signal but fail the three-part test:
- `"Launches"` — GitHub repo, Show HN, or ProductHunt release where the tool exists but no operator is shown running it in production
- `"Tutorials"` — capability or feature explanation written as a walkthrough; no specific named deployment documented
- `"Blueprints"` — not just "how I'd build X", but also architecture / stack / recipe / setup-showcase posts where a real deployment exists yet the post is mainly presenting the system design or operating pattern rather than one clearly bounded workflow with its own outcome. If a post reads like "here is our stack", "here is our recipe", "here are the cron jobs we run", or a deployment tour, prefer `Blueprints` unless it also centers one specific workflow/result strongly enough to pass the core three-part test.
- `"News"` — coverage or commentary about the platform/ecosystem; not a deployment
- `"Analysis"` — head-to-head comparison or benchmark (e.g. "I ran A vs B for 3 weeks") — real usage but the subject is the comparison, not a running deployment
- `"Ecosystem"` — aggregate signals, cohort data, market sizing across many users/products

Additional scope guidance:
- Subreddit / forum flair like `Use Case` is weak evidence only. Do not let forum flair override the content-based scope rules.
- A post can still be `core` even if the title is casual or discussion-framed, as long as the body clearly identifies a named operator, one specific autonomous workflow, and a concrete result/outcome.
- When a real deployment is described but the post mostly inventories several automations, channels, or architectural components rather than focusing on one workflow, default to `Blueprints` instead of `core`.



Tag each qualifying result:

- `category`: Marketing / Productivity / Engineering / Research / Finance / Creative / Other

- `revenue_signal`: true/false — mentions $, ARR, customers, subscribers, income?

- `deep_reasoning`: true/false — involves multi-step iteration, long-running agents, multi-agent coordination, or synthesis across many sources — NOT a single one-shot big-model prompt?

- `uncertainty`: low / medium / high

- `novelty`: low / medium / high



## Step 4 — Build records



For each qualifying use case, produce a JSON object with EXACTLY these keys (matching what ingest.py expects):

Date selection rules:
- `tweetDate` must be the original source/post/article date when it can be determined reliably.
- `searchDate` must be the current run date.
- If the source date is unclear, do not invent a recent `tweetDate`; leave it empty rather than fabricating freshness.



```json

{

  "category": "Marketing|Productivity|Engineering|Research|Finance|Creative|Other",

  "sourceUser": "name of author or publisher",

  "description": "2–3 sentence factual description of exactly what the agent is doing, what the outcome is, and any quantified results (time saved, revenue, scale)",

  "refUrls": "https://source-url-here",

  "tweetDate": "YYYY-MM-DD",

  "searchDate": "YYYY-MM-DD",

  "notes": "id=<sha256_of_refUrls_first_12_hex_chars>; revenue_signal=True|False; deep_reasoning=True|False",

  "uncertainty": "low|medium|high",

  "novelty": "low|medium|high"

}

```

For `increaseScope` entries, add the field (omit entirely for core records):

```json

  "increaseScope": "Launches|Tutorials|Blueprints|News|Analysis|Ecosystem"

```



Key mapping rules:

- `sourceUser` = the author or publisher (NOT "author")

- `description` = the 2–3 sentence summary (NOT "summary")

- `refUrls` = the source URL string (NOT "source_url")

- `tweetDate` = the date of the original post/article (NOT "date")

- `searchDate` = today's date (the date this ingest job ran)

- `notes` = pack the sha256 id, revenue_signal, and deep_reasoning as a single string: `"id=<hash>; revenue_signal=True; deep_reasoning=False"`

- Do NOT include top-level keys named `id`, `author`, `date`, `source_url`, `revenue_signal`, `deep_reasoning`, or `summary` — these will be rejected by ingest.py
- `increaseScope` must be one of: `Launches`, `Tutorials`, `Blueprints`, `News`, `Analysis`, `Ecosystem` — any other value will be rejected by ingest.py

